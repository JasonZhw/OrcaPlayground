## 写在前面

这不是一篇只展示最终效果的“成果说明”，而是一套可以跟着做、可以复现、也可以继续扩展的实训课程。

课程围绕一个清晰的问题展开：

> 如何让 ORCA Lab 场景中的 G1，在不重新训练底层步态的前提下，沿左线或右线前往电气柜，并利用 RGB 颜色占比与彩色桌面保持距离，最终拍摄一张巡检照片？

整个 Demo 采用分层设计：

1. 先确认已有 G1 运控模型能够稳定站立和行走。
2. 再按左右路径点计算 `vx`、`vy` 和目标角度，打通世界坐标到速度控制的闭环。
3. 然后让深色、绿色、黄色 RGB 区域真正影响运动指令，与彩色桌面保持距离。
4. 最后换成更完整、更美观的 Layout，提升展示效果和泛化能力。

这个顺序很重要。视觉导航失败时，我们需要知道问题究竟来自相机、导航逻辑，还是机器人连基本行走都没有做好。分阶段验证能把复杂问题拆成可观察、可定位的小问题。

## 二、认识松应科技与 ORCA

### 2.1 松应科技在做什么

松应科技聚焦机器人仿真、数据与智能训练基础设施。对开发者而言，可以把 ORCA 理解为一套把“场景、机器人资产、物理仿真、传感器数据和算法代码”连接起来的工具链。

本课程不会只停留在图形界面操作，而是同时使用三个部分：

- **ORCA Lab**：搭建和运行可视化仿真场景；
- **OrcaGym**：连接仿真服务，并提供接近 Gymnasium 的环境接口；
- **OrcaPlayground**：放置任务代码、示例、控制器和实验配置。

官方入口：

- 松应科技介绍：<https://www.orca3d.cn/aboutus.html>
- ORCA 产品主页：<https://www.orca3d.cn/home.html>
- ORCA Lab 下载：<https://www.orca3d.cn/download.html>
- ORCA 文档：<https://docs.orca3d.cn/>
- OrcaGym：<https://github.com/openverse-orca/OrcaGym>
- OrcaPlayground：<https://github.com/openverse-orca/OrcaPlayground>

### 2.2 三个部分分别负责什么

初学者最容易把 ORCA Lab 和代码仓库混成同一个东西。更准确的理解是：

| 部分 | 主要职责 | 本 Demo 中的例子 |
| --- | --- | --- |
| ORCA Lab | 编辑场景、加载资产、渲染、运行物理仿真 | 摆放工作台、展示 G1、输出相机画面 |
| OrcaGym | Python 与仿真服务之间的接口 | 查询状态、发送控制、读取传感器 |
| OrcaPlayground | 具体任务和算法代码 | 运控适配、点目标导航、RGB 避障 |

程序运行时，Python 代码并不是在自己的窗口里“重新画一只 G1”，而是通过服务接口让 ORCA Lab 创建或控制场景中的 actor。

### 2.3 资产、Actor 与 Layout

这三个词需要提前分清：

- **资产（Asset/Prefab）**：可复用的机器人或场景对象模板。
- **Actor**：资产在当前仿真场景中的一个实例。
- **Layout**：场景中有哪些物体，以及它们的位置、旋转、缩放等信息。

## 五、Demo 的技术结构

### 5.1 为什么不重新训练 G1 步态

本课程的目标是上层视觉导航，不是从零训练双足运动。已有 locomotion 模型已经能够根据速度指令输出关节动作，因此第一版采用：

```text
冻结低层运控 + 开发上层导航
```

这样做有三个好处：

- 开发周期更短；
- 可以单独验证视觉和导航；
- 上层失败时不会破坏已经稳定的步态。

只有当目标机器人资产、关节定义、执行器接口或运动能力发生根本变化时，才需要考虑重新训练低层。

### 5.2 三层频率

本 Demo 不是所有模块都以同一频率运行：

| 层级 | 频率 | 职责 |
| --- | ---: | --- |
| 物理与 PD | 1000 Hz | 关节级控制与仿真 |
| 冻结 locomotion | 50 Hz | 从速度命令生成 29 维动作 |
| 视觉导航上层 | 10 Hz | 根据目标和图像更新速度命令 |
| RGB 相机 | 约 30 Hz | 提供视觉输入 |

上层无需每个物理步都重新处理图像。更低的决策频率也更接近实际导航系统的分层结构。

### 5.3 速度命令接口

上层只输出：

```text
(forward, lateral, yaw_rate, walk_enabled)
```

含义分别是：

- `forward`：机器人前后方向速度；
- `lateral`：机器人左右方向速度；
- `yaw_rate`：绕竖直轴的旋转速度；
- `walk_enabled`：是否进入行走状态。

当前演示使用较保守的上限：

- 前进最高约 `0.15 m/s`；
- 横移最高约 `0.08 m/s`；
- 转向最高约 `0.35 rad/s`。

慢速并不是算法能力的最终上限，而是考虑到当前头部相机俯角较大，只适合观察近场。速度越快，留给检测和制动的距离越短。

### 5.4 固定 G1 资产的适配

训练参考使用 29-DoF G1 模型，但 `g1_pick_usda` 对外提供 45 个混合执行器：

- 腿和腰：15 个位置伺服；
- 双臂：14 个力矩电机；
- 双手：16 个位置伺服。

因此不能把策略输出的 29 维目标直接写入全部执行器。当前适配层会：

1. 读取 floating base 和 29 个关节状态；
2. 构造冻结策略要求的历史观测；
3. 获取策略动作；
4. 计算策略期望的 PD 力矩；
5. 将腿和腰的力矩反算成位置伺服指令；
6. 将双臂按资产接口控制；
7. 让双手保持安全的零控制。

这也是为什么“能加载 ONNX”不等于“已经能够控制当前资产”。模型输入输出和仿真执行器之间必须有正确的桥接。

## 六、实验一：验证 G1 运控

### 6.1 实验目标

本实验只回答一个问题：

> 不使用导航和相机时，固定 G1 资产能否执行基础速度指令，并保持稳定？

它会依次测试：

- 原地站立；
- 向前行走；
- 左转；
- 向左横移；
- 停止并保持站立。

### 6.2 运行

先启动 ORCA Lab，然后在新终端执行：

```bash
conda activate orca
cd /home/jason77/SY/OrcaPlayground
python examples/euler/g1_vision_nav/validate_locomotion.py
```

覆盖出生点和朝向：

```bash
python examples/euler/g1_vision_nav/validate_locomotion.py \
  --spawn-x -18.5 \
  --spawn-y -13.5 \
  --spawn-yaw 0
```

程序会清空 ORCA Lab 当前运行场景，并从 Layout JSON 重新发布场景和 G1。所以运行前务必保存 Layout。

### 6.3 `num-steps` 是什么

脚本的 `--num-steps` 表示 50 Hz 低层控制步数：

```text
仿真时长（秒）≈ num_steps / 50
```

例如：

| `num-steps` | 约等于 |
| ---: | ---: |
| 500 | 10 秒 |
| 1000 | 20 秒 |
| 4000 | 80 秒 |

增大它只会让实验运行更久，不会自动提高速度。

### 6.4 观察指标

不要只看“机器人有没有动”。至少记录：

- 基座高度是否保持在合理范围；
- roll/pitch 是否持续增大；
- ONNX 输出是否全部为有限数值；
- 关节力矩是否长时间触限；
- 停止后是否仍能稳定站立；
- 是否出现身体与环境的非预期碰撞。

本实验当前通过条件包括：

- G1 不跌倒；
- 基座高度约在 `0.6–0.9 m`；
- 策略输出没有 `NaN` 或无穷大；
- 没有持续力矩触限。

### 6.5 已验证结果

2026-08-21，完整 1000 步测试结果：

```text
82/82 passed
```

其中：

- 站立、`0.5 m/s` 前进、左转、`0.3 m/s` 侧移和停止全部通过；
- 基座高度约 `0.729–0.790 m`；
- 最大俯仰/横滚倾角约 `0.084 rad`；
- 策略输出始终有限；
- 统计到的力矩触限比例为 0。

### 6.7 常见失败

**报错 `ModuleNotFoundError: No module named 'envs'`**

请从仓库根目录执行当前版本脚本。当前脚本会把项目根目录加入 `sys.path`；不要把旧的临时验证脚本复制到其他目录运行。

**机器人不动，但没有 Python Traceback**

依次检查 ORCA Lab 是否运行、actor 名称是否是 `g1_pick_usda`、资产路径是否正确，以及服务是否在 50051。

**机器人一生成就摔倒**

通常优先排查出生高度、是否生成在桌子内部、执行器映射、控制频率和策略配置，而不是直接修改 reward。

## 七、配套预检：确认相机可用

虽然定点导航不依赖像素，但在进入视觉避障前，必须独立验证相机。

### 7.1 当前相机结论

固定 G1 资产包含三路 ORCA Lab Studio Camera Component：

| 相机 | 端口 | 用途 |
| --- | ---: | --- |
| `camera_head` / `head_cam` | 7072 | 本 Demo 的头部 RGB |
| `camera_left` | 7071 | 左侧 RGB |
| `camera_right` | 7070 | 右侧 RGB |

在线抓帧已确认三路都是独立的三通道 RGB，并不是 RGB、Depth 的组合。真正的米制深度端点尚未确认，因此本课程当前不能根据这三路图像直接声称获得了障碍距离。

### 7.2 为什么模型里 `ncam=0` 仍然有图像

在线导出的 MuJoCo XML 中没有 `<camera>`，所以 MuJoCo 模型统计可能显示 `ncam=0`。但资产还可以包含 ORCA Lab Studio 侧的 Camera Component，其画面由 Studio 渲染并通过 WebSocket 输出。

因此：

```text
MuJoCo ncam=0 ≠ ORCA Lab 资产一定没有相机
```

应以资产组件和在线抓帧结果为准。

### 7.3 运行相机验证

```bash
conda activate orca
cd /home/jason77/SY/OrcaPlayground
python examples/euler/g1_vision_nav/validate_camera.py
```

程序会：

1. 重建 Layout 并生成固定 G1；
2. 激活头部 Camera Component；
3. 让仿真先执行 step 和 render；
4. 检查首帧、帧号增长、分辨率、类型和非空内容；
5. 保存样本到 `/tmp/g1_camera_head_rgb.png`。

### 7.4 当前视角的限制

头部画面方向是正立的，但俯角较大，主要看到手臂、脚和近处地面，远处地平线不明显。

当前策略是：

- 接受现有资产，不修改机器人本体；
- 把它当作 1～2 米范围的近场安全相机；
- 限制最高速度；
- 遇到桌子时提前减速并横移；
- 将高速、远距离规划留给后续带更合适前视相机的资产版本。

现有 Python 公共接口可以激活相机并修改分辨率、FOV、裁剪面和流端口，但不能持久化修改 Studio Camera Component 的位置和旋转。相机角度调整应在资产或预制体侧完成。

## 八、实验二：定点导航

### 8.1 实验目标

让 G1 从出生点自动走到指定世界坐标，同时保持低层 locomotion 模型冻结。

这一阶段会验证：

- 世界坐标目标是否读取正确；
- 目标能否转换到机器人坐标系；
- 上层输出能否正确进入速度命令桥；
- G1 能否转向、横移并收敛到目标；
- 到达后能否停止并保持站立。

这一阶段虽然持续检查 RGB 是否产帧，但点目标控制器不读取像素。这样可以先排除视觉算法的影响。

### 8.2 坐标系

世界坐标中的目标为：

```text
goal_world = (goal_x, goal_y)
```

根据机器人当前位置与 yaw，把目标变换到机器人坐标系：

```text
goal_robot = (x_forward, y_left)
```

在本课程约定中：

```text
x_forward > 0：目标在机器人前方
y_left > 0：目标在机器人左侧
```

控制器根据距离和方位角产生前进、横移和转向速度。大角度误差时先转向，接近目标时降低速度。

### 8.3 默认运行

```bash
conda activate orca
cd /home/jason77/SY/OrcaPlayground
python examples/euler/g1_vision_nav/run_point_goal.py
```

默认目标位于出生朝向前方约 1 米。

指定绝对世界坐标：

```bash
python examples/euler/g1_vision_nav/run_point_goal.py \
  --goal-x -18.5 \
  --goal-y -12.7 \
  --num-steps 900
```

### 8.4 安全逻辑

程序持续检查：

- 基座高度；
- 机器人倾角；
- 策略输出；
- 力矩触限；
- RGB 帧增长；
- 非足部环境碰撞。

脚与地面的正常支撑接触允许。跌倒或状态异常会保持速度急停；机器人身体持续撞到场景物体时先停 1 秒，再依据 RGB 左右占比向较空一侧执行 5 秒脱困，避免停止后因接触无法清除而永久锁死。

### 8.5 已验证结果

2026-08-21 的在线结果：

- 前方点目标：初始距离 `1.323 m`，最终 `0.310 m`，`125/125 passed`；
- 左侧点目标：最终 `0.313 m`，最小 `0.296 m`，`156/156 passed`；
- 两次测试均未跌倒；
- 未检测到非足部环境碰撞；
- 7072 RGB 全程连续产帧。

这里的“到达”不是要求数学意义上的零误差，而是进入设定的目标容差，然后停止行走。

### 8.6 对照实验

建议至少做三条路线：

| 路线 | 目的 |
| --- | --- |
| 正前方 1 米 | 验证前进与停止 |
| 左侧目标 | 验证转向、横移和坐标变换 |
| 右后方目标 | 验证较大偏航误差下的行为 |

每次记录：

- 初始距离；
- 最小距离；
- 最终距离；
- 到达步数；
- 是否跌倒；
- 是否发生身体碰撞；
- 是否持续收到 RGB。

4. 解释为什么这一阶段不能称为“视觉导航”。

## 九、实验三：桌子场景的 RGB 避障

### 9.1 实验目标

让头部 RGB 不只是被读取，而是真正改变 G1 的速度指令。

当前 Layout 中有绿色台面的工业工作台。第一版选择可解释、容易回归的视觉基线：

1. 在头部 RGB 的近场区域检测绿色像素；
2. 估计画面左侧和右侧的风险；
3. 风险升高时限制前进速度；
4. 向更空的一侧横移并转向；
5. 障碍刚离开画面后保持一段时间的绕行动作；
6. 清除障碍后重新收敛到点目标。

### 9.2 为什么先做颜色基线

颜色检测不是最终视觉方案，但作为第一版有明显价值：

- 每一步决策都能解释；
- 容易判断 RGB 是否真的进入控制回路；
- 不需要先采集和标注大规模数据；
- 可以形成稳定回归测试；
- 能快速暴露相机延迟、视角和控制耦合问题。

教学中必须明确它的能力边界：

> 当前结果证明的是“能利用 RGB 识别当前绿色工作台并绕行”，不是“已经能识别所有桌子和所有障碍物”。

### 9.3 默认验证路线

默认出生点：

```text
(-18.5, -13.5)
```

默认目标：

```text
(-22.0, -15.7)
```

直线路径会接近 `industrial_workbench_1`，适合验证视觉是否介入。

运行：

```bash
conda activate orca
cd /home/jason77/SY/OrcaPlayground
python examples/euler/g1_vision_nav/run_visual_avoidance.py \
  --num-steps 4000
```

覆盖目标：

```bash
python examples/euler/g1_vision_nav/run_visual_avoidance.py \
  --goal-x -22.0 \
  --goal-y -15.7 \
  --num-steps 4000
```

### 9.4 视觉风险

当前检测器关注画面上方约 72% 的近场区域，并计算：

- 绿色区域总体占比；
- 左半边风险；
- 右半边风险；
- 建议绕行方向。

当风险较小时，继续由点目标控制器主导；当风险超过阈值时，视觉层覆盖部分速度：

```text
基础目标指令
      │
      ▼
RGB 风险判断
      │
      ├── 低风险：保持目标跟随
      │
      └── 高风险：减速 + 横移 + 转向
                         │
                         ▼
                    安全限幅
```

### 9.5 为什么需要“绕行保持”

早期版本存在一个典型问题：

1. 相机看见桌子，机器人开始绕行；
2. 桌子暂时离开近场画面；
3. 视觉风险立刻降为零；
4. 点目标控制器马上转回目标；
5. 机器人可能擦碰桌边或在边缘反复摆动。

解决方法是在障碍离开画面后继续保持约 6 秒的低速斜向绕行，让身体完全通过桌边后再恢复目标跟随。

这个案例很适合教学：感知“这一帧看不见障碍”不等于几何上“机器人已经安全通过障碍”。

### 9.6 已验证结果

2026-08-21，默认路线在线运行结果：

```text
655/655 passed
```

关键指标：

- 初始目标距离：`3.864 m`；
- 最终目标距离：`0.309 m`；
- 最小目标距离：`0.293 m`；
- RGB 风险峰值：`0.0569`；
- 视觉层介入：282 个 10 Hz 决策步；
- 未跌倒；
- 未发生非足部环境碰撞；
- 7072 RGB 持续产帧；
- 约在 step 2400 到达，之后站立到 step 4000。

### 9.7 这一结果不能证明什么

当前基线尚不能证明：

- 能识别任意颜色和材质的桌子；
- 能处理透明物体；
- 能从单目 RGB 得到可靠的米制深度；
- 能处理移动障碍物；
- 能完成全局路径规划；
- 能在完全陌生的 Layout 中直接泛化；
- 能用于真实 G1，无需额外标定和安全验证。

### 9.8 学员任务

1. 运行默认路线并观察视觉介入次数。

5. 用一句准确的话描述 Demo 能力，避免夸大为“通用视觉导航”。

### 10.1 Layout 2.0 的设计目标

新场景建议满足：

- 关键物体不遮挡主镜头；
- 俯视镜头能同时看到 G1、障碍和目标；
- 场景中保留安全缓冲区，避免出生即碰撞；
- Layout 可以保存、导出并由脚本重复生成。

### 10.2 建议的四条验证路线

| 路线 | 场景 | 验证内容 |
| --- | --- | --- |
| A | 空旷直线 | 运控和基本到达 |
| B | 单桌阻挡 | RGB 介入和单次绕行 |
| C | 两个错位桌子 | 连续局部决策 |
| D | 桌子与货架组合 | 新外观下的泛化与失败边界 |

路线 A、B 应作为固定回归测试。路线 C、D 可以用于后续算法迭代，不能因为失败就删除。

### 10.3 场景资产记录表

每次从资产中心选环境或物体时，记录：

| 字段 | 示例 |
| --- | --- |

| 编辑器显示名 | 工业工作台 |
| 生成后的 actor 名 | `industrial_workbench_1` |
| 推荐出生点 | `x, y, z, yaw` |
| 可行走范围 | `x_min, x_max, y_min, y_max` |
| 碰撞体是否有效 | 是/否/待确认 |

不要只保存资产缩略图或中文显示名。程序稳定重建场景需要完整 Path 和 actor 信息。

### 10.4 从颜色规则走向通用感知

当 Layout 2.0 包含不同颜色、材质和光照后，应保留当前绿色工作台检测器作为回归基线，同时增加类别无关的感知方案。

推荐路线：

1. 记录 RGB、位姿、速度命令、碰撞和视觉介入；
2. 增加可用于监督或评估的障碍标记；
3. 选择深度估计、分割、占用预测或学习型策略；
4. 输出仍保持 `(forward, lateral, yaw_rate)`；
5. 不直接让图像网络控制 29 个关节；
6. 从稀疏静态障碍开始，再增加纹理、光照和布局随机化。

第一版训练观测可以定义为：

```text
缩放 RGB
+ 目标在机器人坐标系中的 (x, y)
+ 本体平面速度
+ 偏航角速度
+ 上一条速度指令
```

动作：

```text
forward, lateral, yaw_rate
```

奖励：

- 正奖励：目标距离减少、到达目标；
- 负奖励：碰撞、跌倒、超时、动作突变、长期无进展。

课程建议依次使用：

```text
空旷目标跟随
→ 稀疏静态障碍
→ 密集障碍与拐角
→ 纹理和光照随机化
→ 巡检点序列
```

6. 找到结果和截图；
7. 根据 FAQ 解决至少一个人为制造的问题。

如果必须由开发者口头补充才能成功，说明文档仍不够完整。

## 十三、常见问题

### 13.1 ORCA Lab 里已经拖了 G1，脚本为什么又生成一只？

当前脚本会先清空运行场景，再根据 Layout JSON 重建场景，并使用固定资产路径生成 G1。推荐让脚本成为唯一的 G1 生成来源，避免名称冲突、重复 actor 和初始位置不一致。

### 13.2 直接在编辑器里调整场景会保存到代码仓库吗？

不会自动保存。需要导出或保存 Layout JSON，并把它纳入教学包。编辑器临时状态、资产中心内容和 Git 仓库是三个不同层次。

### 13.3 为什么运行脚本会清空当前场景？

这是为了让实验可重复：每次都从同一个 Layout 和出生点开始。清空前必须确认所有需要保留的编辑器修改都已经导出。

### 13.4 `ncam=0` 是否说明 G1 没有相机？

不一定。这里的 G1 使用 Studio Camera Component，通过独立 WebSocket 输出 RGB；它不一定出现在 MuJoCo `<camera>` 统计中。

### 13.5 7070 是不是深度图？

不是。在线验证显示 7070、7071、7072 都是三通道 RGB。没有确认深度端点前，不能把任何一路当作米制 depth。

### 13.6 为什么相机看得很近？

固定资产的头部相机俯角较大。当前 Demo 通过低速和近场避障适配这个视角；若要高速、远距离导航，应在资产侧增加更合适的前视相机。

### 13.7 为什么不让视觉网络直接输出关节动作？

本课程关注导航。让上层只输出速度，能够复用稳定的 locomotion，降低训练难度，并把感知失败与步态失败分开。

### 13.8 到达目标后为什么程序还没有退出？

到达后 G1 会停止行走并站立，直到 `num-steps` 用完。这样可以观察停止状态是否稳定。

### 13.9 为什么机器人在桌子边缘来回摆动？

常见原因是障碍刚离开相机画面，目标控制器就立刻转回。当前版本加入了约 6 秒的绕行保持。若新 Layout 仍振荡，应检查保持时间、速度、相机视野和目标位置。

### 13.10 Warning 和 Traceback 有什么区别？

Warning 提醒存在兼容或降级行为，程序可能继续运行；Traceback 表示 Python 执行失败。排查时先看 Traceback 最后一行，再判断是否与前面的 Warning 有关。

### 13.11 checkpoint 为什么可能加载失败？

文件未完整下载、传输中断、保存失败或 PyTorch 版本差异都可能导致加载问题。先检查文件大小和哈希，不要通过修改 `torch.load` 参数掩盖损坏的压缩包。

### 13.12 `pip install -e .` 为什么报 `build_editable`？

这通常是项目构建后端或安装工具版本不支持 PEP 660 editable install。应按照 OrcaGym 当前仓库说明安装，并确认 `pip`、构建依赖和 Python 版本；它与 G1 控制逻辑无关。

### 14.1 开场演示

先播放 20～30 秒最终避障片段，再展示系统分层图。这样学员能先知道最终目标，再理解为什么课程从运控开始。

## 结语

这个 Demo 最有价值的地方，不是“让 G1 动起来”本身，而是建立了一条可逐层验证的机器人开发链路：

```text
先让它稳定走
→ 再让它走到目标
→ 再让图像影响动作
→ 再让它在更复杂的场景中泛化
```

前三步已经在当前 ORCA Lab 场景中跑通。下一阶段不需要推翻现有代码，而是围绕 Layout 2.0、数据记录和更通用的视觉感知逐步扩展，同时始终保留运控、点目标和单桌避障三条回归基线。
